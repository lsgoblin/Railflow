# Design Summary

Sihan Li | 2453202 | Single-author project | CD-20261119 | 2026-11-19

RailFlow takes map-based ticket search and railway line display as the starting point for the redesign of the system. In this workflow, the user selects a city and a set of travel conditions; the system then assembles historical railway reference itineraries, each of which retains its source, and it matches the travelled segments against actual railway track geometry, which is then shown over a real basemap.

The Part I submission and the classroom presentation version of the project contain the complete set of flows, covering ticket search, seat locking, payment, refund, and administration. The author relays that the teacher considered the original scope of the project too large and unrealistic, and the teacher recommended focusing the project on a single distinctive feature of the system, such as map-based ticket search. The author refactored the project in response to this assessment. A budget constraint further led the system to adopt fixed historical timetables, to display a missing price as unknown, and to make no promise that a service currently operates or that it is available for sale. The map must be associated with actual railway geometry, and schematic lines cannot stand in for it.

The new version retains the established technology stack of Java 17, Spring Boot 3, MyBatis, MySQL 8, and native ES Modules. The backend remains a single monolithic service, and its internal responsibilities are divided among place, planning, geometry, AI orchestration, and saving. Service day, times that cross midnight, and itinerary date are modeled as three separate concepts; the length of a stay is measured in calendar days rather than in service days; recommendations give priority to the itinerary that requires the fewest transfers. The AI component only interprets the user's intent; railway facts are verified by deterministic services; and multi-round edits operate on the same itinerary version, which prevents an older response from overwriting a newer edit.

On 2026-11-17 the project scope converged to two core capabilities: the whole-package import of a fixed GTFS package, and the actual railway track geometry of the segment between any two stations on the same train run, overlaid on a real basemap. Together these two capabilities form a closed MVP loop of 16 items, each of which is ready for acceptance by the user; AI, fares, saving, and transfers are deferred beyond this loop. The implementation was completed in the period from 11-18 to 11-19: the whole-package import loaded about 4.78 million rows of GTFS data, the backend hosts the frontend same-origin, the segment track geometry of three sample train runs was checked segment by segment against the real basemap, and all 16 MVP items passed independent review and item-by-item acceptance by the user. Cross-browser and real-device checks, together with concurrency stress testing, are still to be verified, and the product AI remains at the design stage; see the feature list.
