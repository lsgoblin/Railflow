## 1. 项目定位与当前范围

RailFlow 是 **AI 铁路行程助手与城际铁路路线规划系统**。用户通过地图点选城市或 AI 对话提出出行想法，系统匹配具体铁路车站，基于有来源的历史车次、时刻和区间席别票价组织参考行程，并在主页地图沿实际铁路走向点亮对应路线。

当前只做铁路出行。景点、住宿、酒店预订、旅游每日活动安排、市内公交/地铁/驾车、飞机或汽车方案不属于当前范围。停留天数只用于安排后续铁路行程，不扩展为当地游玩规划。

铁路线路、历史数据和 AI 各有职责：铁路几何提供实际走向；历史数据提供车次、时刻及参考票价，保留版本与适用范围；AI 负责理解偏好、补充询问、提出方案与解释，不能自行编造这些事实。当前不查询、模拟或根据余票筛选，不承诺实时开行、当前价格或可售性。

## 2. 已确认的决策

1. **地图点选城市组线**：用户依次点击城市形成有序路线，系统按城市顺序检索对应铁路方案。
2. **车站自动匹配**：用户点选城市且未指定车站时，按同城候选站的 `stop_id` 字典序升序尝试，第一站为默认候选。最终选站按全程换乘次数推荐。全部候选无解时保留城市输入，对应路线不展示。按用户明确指定的车站匹配。城市、具体车站和列车运行实例分开表达。
3. **不设换乘次数上限**：不以“一次、两次、三次”等固定值限制用户路线，也不静默截断城市序列。
4. **默认停留一天**：每个用户选定的停留节点默认一天，可逐个修改；按到达后的下一自然日可继续出发计算，不要求满 24 小时。
5. **默认换乘最少**：用户所说“最短”指全程换乘次数最少，同站换另一班车也计一次。直达车次优先参与搜索，全程换乘次数决定推荐结果。
6. **零换乘沿用默认路线**：存在可行的默认直达方案时，沿用它的实际铁路运行路线，不为了里程更短或更早到达额外改线。
7. **历史数据规划**：使用历史车次、实际发到站、时刻与历史区间席别价格，注明来源及版本；不依赖收费票务 API。
8. **AI 个性化与多轮修改**：AI 可理解“今天坐火车慢摇到哈尔滨”等意图，后续补充“途经郑州”时保留仍有效的上下文并更新方案。
9. **保存个性化输出**：生成方案与后续调整应可保存、恢复并继续修改，不能只保留一次回复文字。
10. **缺失信息回复**：缺少必要信息或没有固定关键词时，AI 给出相关回复、补问或引导，不清空已有行程。
11. **区域目的地先建议再预览**：用户只说“想去新疆”，AI 可先明确建议乌鲁木齐等具体城市，点亮可修改预览；建议不等于用户已经指定。
12. **主页点亮实际铁路线路**：不能用城市直线、道路算路、站点折线或 AI 生成坐标替代实际铁路走向。
13. **最简模拟预订**：保留“选方案 → 确认 → 模拟记录”作为配套；主要实现重点是规划、AI 与地图。
14. **余票暂不处理**：本轮不查询余票、不构造模拟余票、不按余票排除或推荐路线；界面与 AI 不给出“有票/无票/已核实可售”结论。
15. **地点数据分工**：本地仅维护城市与对应铁路客运站点，包括普速、高铁及兼有服务的车站；其他地点通过高德 API 按需查询，不建设全量本地地点库。历史铁路数据和实际铁路几何是独立数据，不因点位范围收缩而取消。
16. **GTFS 与关联轨迹**：铁路站点、车次、时刻和开行日历采用 `wensimehrp/chinese-railway-gtfs`；地图轨迹使用同一发布包经 `trips.shape_id` 关联的 `shapes.txt`，选中区间须通过几何核验。
17. **固定多日版本初测**：先固定一个实际可用、覆盖连续多日的版本测试少量路线，不强制使用上一年同月同日；行程日期与数据参考日期明确区分，按统一日期偏移回放，不冒充当前实际开行。

## 3. 两种入口与共同主流程

### 3.1 地图入口

用户在主页地图上依次点选城市，例如：

```text
北京 → 南京 → 上海 → 南宁
```

该序列是用户的行程约束。系统匹配各城市的具体车站、检索历史分段车次与参考票价、检查停留日期与前后程衔接，展示路线和方案。找不到衔接时不能擅自跳过城市、改换目的地或调整用户已确认的顺序。

新增点选城市触发自动重算，允许调整需要重新匹配的自动到发站及车次。点选的中间城市默认停留一天。系统按全程换乘最少推荐，并展示选中方案的换乘点。主页使用同一份行程，详见 [城市行程历史回放](city-replay.md)。

用户之前举出的“北京西 → 南京南 → 上海虹桥 → 南宁东”只是具体站点层面的示例。实际车站由真实数据和用户调整确定，不硬编码为唯一结果；本文件没有验证这条站点链的车次、时刻、价格或可售性。

### 3.2 AI 入口

用户可以只表达目的地和偏好，由 AI 理解意图并调用规划能力生成候选铁路路线，无需先手动点完中间城市。AI 建议的城市和用户明确要求的途经城市必须可区分。用户可继续通过对话或地图编辑同一方案。

AI 自动生成候选路线不代表对全国铁路进行无限穷举；线路与车次必须有数据依据。用户明确要求的途经、停留和车站选择不能被生成式建议覆盖。

### 3.3 共同流程

1. 接收城市序列或自然语言，恢复当前行程中仍有效的条件。
2. 确定出发地、目的地/建议目的城市、首次出发日期与必要出行条件；缺失时按 §7 处理。
3. 自动匹配车站，生成有真实铁路连接依据的候选线路。
4. 在选定历史数据版本及日期口径下，按实际乘坐区间和席别检索车次、时刻与历史票价，显示缺失字段。
5. 校验停留、历史时刻衔接与用户条件，按换乘最少推荐参考方案；不进行票额校验。
6. 同步更新 AI 回复、主页实际铁路高亮、分段列表及保存的当前行程。
7. 修改城市、车站、停留或偏好后，重算受影响及后续日期依赖段；模拟预订是独立的配套操作。

## 4. 车站、停留与日期规则

### 4.1 城市与车站

地图以城市为输入，历史车次匹配必须落到具体上车站、下车站。城市与车站的对应关系由本地基础数据维护并可追溯，不由 AI 猜测；车站有稳定标识，同一客运站兼有普速和高铁服务时不重复建成两个站。高德地点标识不能直接充当铁路站码。

多站城市的候选站来自本地城市与车站的已核实关联。用户未指定车站时，按 `stop_id` 字典序升序排列候选，以第一站为默认候选。其他候选可在全程换乘更少时被选中。全部候选均无可行路线时，保留城市和其他有效输入，不展示受影响的路线。若用户已指定车站，按该站匹配，是否改站由用户决定。

单段的两端均有多个自动候选时，先固定当前出发候选，依次尝试到达候选，再换下一个出发候选。城市目录和自动规划边界见 [城市行程历史回放](city-replay.md)。

系统可以安排同城跨站换乘，同时展示实际到站与下一程离站。跨站接驳用时和最小衔接缓冲的来源与校验口径待确定。缺乏核验依据的跨站方案不标为已验证可衔接。

### 4.2 默认停留一天

“每站一天”指用户选定的行程停留节点，不是列车普通经停站，也不是规划服务补齐的每个铁路网络节点。

默认按自然日计算：周一到达南京，周二即可继续出发，不需要等到周二的相同时刻。每个停留节点可以单独调整。实际出发时刻仍须满足车次、必要衔接缓冲和用户时间条件。

若前段跨日抵达，后续日期按方案到达日重新计算。例如周三才抵达上海，则上海默认后续出发日期从周四开始考虑。调整停留或前段车次后，重新计算受到影响的后续历史车次匹配与衔接。

起点由首次出发日期确定；终点没有下一段车次需要自动检索。首次出发和停留后续程只匹配各自首个可出发自然日上车的车次。同站换乘按调用方提供的最短换乘间隔衔接，允许跨午夜。零天同日续乘留待细化。开行以列车自身的参考服务日历为准。

## 5. 默认推荐与换乘计数

默认先满足用户明确的城市顺序、车站、日期、停留、席别等条件，并验证所选历史时刻中的衔接，再按 **全程换乘列车次数从少到多** 推荐。各段可先搜索直达。有可续程的直达候选时，仍须比较可能减少全程换乘次数的换乘方案。界面使用“换乘最少”说明口径，本轮不将余票作为约束。

- 改乘另一列车计一次换乘，即使仍在南京南站内换车。
- 南京南到南京站后改乘另一列车，也计一次列车换乘；跨站接驳另行展示和校验。
- 同一列车运行实例途经多个站，或同一次乘车分成多个展示/售票区间，不因此增加换乘次数。
- 不能按绘制城市数、站点数或分段卡片数直接计算换乘次数。
- 零换乘可行时优先直达；已有可行默认直达方案时，沿用该方案的实际铁路运行路线。
- 不能通过忽略用户途经城市、一日停留或时刻冲突来人为得到“零换乘”。

“换乘更少优先”和“不设次数上限”同时成立：前者是推荐顺序，后者是产品范围。同等换乘次数时的次级排序尚待确定，不默认引入价格、耗时或里程的优先级。

## 6. 历史数据与票价规则

下表是需求字段，不是已定稿的接口或数据库结构。

| 数据 | 需求口径 |
| --- | --- |
| 城市与具体车站 | 本地维护城市及所属铁路客运站的稳定标识、名称/别名、行政归属、坐标及坐标系、来源/版本；车站匹配铁路数据标识。能区分上/下车站，不能误用整趟列车始发/终到站。 |
| 历史车次与版本 | 展示车次及数据版本，区分运行实例或数据中的适用日期；不能仅按车次字符串拼接不同年份的时刻与票价。 |
| 日期与时刻 | 按 §6.2 的行程日期/数据参考日期、固定日偏移与服务日组织完整时刻；北京时间口径保留，支持超过 24 小时的 GTFS 时刻，不暗改“今天”。 |
| 历史席别与区间票价 | 对应数据版本、实际乘坐区间、席别和币种；注明来源及年份/采集日；缺失价格显示未知，不按零汇总或自动填模拟价格。 |
| 实际铁路几何 | 连续铁路线路、数据来源、与目标区间及已选车次的匹配依据；不能拿道路或直线替代。 |
| 来源与信息时间 | 保留原始来源、数据快照/适用版本和导入时间；本地读取时间不冒充历史票价采集时间或实时更新。 |

规划和展示遵守以下规则：

1. 优先选择可匹配同一数据版本的车次、时刻和区间票价；历史票价必须对应本段上下车站和席别。版本不同或字段不足时明确标注，无法核对时按未知处理。
2. 不用当前价格冒充历史价格，不把不同年份同名车次直接拼接；不通过全程票价相减、按公里估算或随机生成来冒充历史区间价。
3. 显示“历史票价（数据年份/版本）”，表示参考金额，不承诺当前售价。部分缺失时显示已知历史票价合计与缺失段数，不能称为完整总价。
4. 历史票价缺失不自动使一条可衔接路线消失；保留线路并显示费用未知。需要按预算筛选时，价格不全的方案不能被当作已满足预算。
5. 依据历史时刻判定的是该数据版本内的参考衔接；没有匹配车次、数据缺失、日期不覆盖和载入失败应分别表达。部分成功不等于整条路线完成校验。
6. 总耗时按方案最终到达减首次出发计算，包含等待与停留；后段日期及列车始发日/旅客上车日的对应按数据字段校验。
7. 保存、恢复或修改行程时保留并核对数据版本；版本改变后重算，不要求实时票价/余票刷新，也不把旧数据描述为今天的售票事实。
8. 当前不查询或保存余票快照、不生成模拟票额，不据票额过滤或排序，不提供“有票/无票/候补/已核实可售”状态。面向用户说明历史参考属性及未核验当前余票即可。
9. 找不到可衔接方案时指出受影响段，保留输入和有效结果，允许用户改条件，不擅自删城市、改日期或换掉明确指定的车站。

本轮使用下述固定 GTFS 快照作为本地规划输入，不接入真实/收费票务 API。数据源、轨迹关联和日期回放方式已确认；历史票价及城市归属仍需另补，当前仅完成公开源码与发布包内存抽查，未将数据落地导入项目。票务服务接入与余票处理仅为后续可选方向，不作为本轮交付依赖。

不设换乘次数上限不等于承诺无限计算资源。每次提交仍是有限城市序列；分段计算、进度和错误处理需要设计，但不能静默截断行程或把未处理段当作已完成。

### 6.1 GTFS 来源与固定版本

铁路主数据源为 [chinese-railway-gtfs](https://github.com/wensimehrp/chinese-railway-gtfs)，使用 Releases 的预生成 `output_gtfs.zip`，不要求运行上游 Python 爬虫。按仓库 CC BY 4.0 许可保留作者、来源、版本及必要变更说明。

初测固定为此前已在内存中读取的 [gtfs-20261116-085531](https://github.com/wensimehrp/chinese-railway-gtfs/releases/tag/gtfs-20261116-085531)。`feed_info.txt` 的版本为 `20261116`，整体日期范围为 2026-11-01～2027-02-02；这不代表每趟车在整个范围内每天开行，仍逐车检查日历。测试期间不自动切换最新包；落地导入时记录来源 URL、文件哈希和实际覆盖日期，版本替换后重新核验样例并重算旧结果。

| 文件 | 本项目用途 |
| --- | --- |
| `stops.txt` | 站名、`stop_id` 与 WGS84 坐标；城市归属、别名及普速/高铁服务标签另补，不单凭站名截取城市。 |
| `trips.txt` / `routes.txt` | 车次展示、`trip_id`、`service_id` 与 `shape_id` 关联；本仓库的 `route_id` 为车次标识，不等同于用户多城市行程。 |
| `stop_times.txt` | 按 `trip_id` 与 `stop_sequence` 取得乘坐区间及累计跨日时刻。 |
| `calendar_dates.txt` | 校验参考服务日是否开行；该包没有 `calendar.txt`，不默认每天运行。 |
| `shapes.txt` | 经 `trips.shape_id` 关联，按 `shape_pt_sequence` 排序；可被多个车次共享，也可能缺失。 |
| `feed_info.txt` | 版本及整体日期范围，不替代逐车开行日历。 |

该仓库不含票价，历史区间/席别价仍需独立来源，未补齐显示未知，不填模拟报价；回放不改变价格的原始年份。运行实例按数据版本、`trip_id` 与参考服务日区分，不能混用不同版本的内部标识。站点坐标存在缺失插值的可能，目标样例站点需核对坐标来源与准确性。

### 6.2 初测日期与历史回放

初测选实际可用且覆盖样例连续多日的服务日，不强制去年同月同日。每个初测场景固定“行程基准日 D0 / 数据参考基准日 R0”和数据版本；基准日由导入核验后从样例可开行日期中选定，属于测试配置。若版本覆盖目标日期，可令 D0 与 R0 相同，直接使用该日数据。

1. **统一偏移**：按北京时间自然日计算 `偏移天数 = D0 - R0`；查询参考日等于行程日减偏移，展示行程日等于参考日加偏移。所有区间、停留和续程使用同一偏移，不对每一天分别减一年。
   回放始终使用固定北京时间 `UTC+08:00`、24 小时制，停用夏时制。日期偏移保留参考发到钟点和原始 GTFS 累计时刻。
2. **服务日与上车日**：按参考服务日检查 `service_id` 开行记录，再将 GTFS 累计时刻加到服务日零点。途中上车自然日可能晚于列车服务日，不能仅按旅客上车日查日历。
3. **跨日**：`26:06:00` 为服务日次日 02:06，`56:20:00` 为第三个自然日 08:20；按累计秒数构造完整参考发到时间，再加日偏移。不能先取模 24 丢掉日偏移，也不能将该字段直接解析为普通 `LocalTime`。
4. **停留**：到达后按行程日期计算下一自然日可出发，再换回后段参考日期查询；跨日、等待与停留时长保持。自动中转站不自动成为停留一天的访问节点。
5. **今天与展示**：“今天/明天”仍按服务端实际北京时间解析；主日期显示行程日期，统一短标显示“历史回放”和参考日期/版本，详情可查看两套完整日期。不修改系统时钟，不称为今天真实开行。
6. **边界**：参考日无开行记录或超出覆盖时分别说明无匹配/日期不覆盖，不自动换包、换日或视为开行。跨月、跨年及闰日按连续日偏移处理；不假定同月同日具有相同星期、节假日或运营条件。
7. **恢复与修改**：保存版本、D0/R0、原始参考服务日/时刻与行程日期，恢复时不按当天重新生成偏移。改日期沿用该行程锚点重算；明确更换版本或锚点后旧结果待重算，地图、AI 与列表同步，历史票价年份保留。

例：2026-11-16 出发、17 日到达、18 日续程，若 R0 为 2025-11-16，则查询相应的 2025-11-16～18。此例仅说明规则，所选 2026 版包并不因此包含 2025 年数据；实际参考日必须来自固定包的有效日历。日历与时刻依 [GTFS Schedule 规范](https://gtfs.org/documentation/schedule/reference/)处理。

## 7. AI 个性化、多轮修改与保存

### 7.1 意图理解与个性化输出

AI 理解完整自然语言，提取出发地、目的地、相对日期、途经约束、停留和出行偏好。不能只在命中特定关键词时才响应，也不能仅生成与地图和车票无关的文字攻略。

“慢摇到哈尔滨”可以作为慢节奏铁路出行倾向回显并允许纠正，不擅自认定必须某一车型、席别或无限长的乘车时间。明确的用户条件优先，含糊偏好作为可调整建议。

“今天”以服务端实际北京时间解析，按 §6.2 的固定锚点与统一偏移转换参考日期；AI 回显行程日期并说明历史回放版本，不把历史服务日描述为今天的开行事实。方案内车次仍需符合参考服务日历与衔接条件。

### 7.2 区域目的地与对话样例

以下描述目标行为，不是已经查询到的实际线路或票务结果。

| 用户表达 | 预期行为 |
| --- | --- |
| “今天我想坐火车慢摇到哈尔滨” | 理解目的地、日期和偏好；补齐必要上下文，基于历史数据回复参考行程与历史票价，并在主页点亮有依据的实际铁路路线，不声称已核验当前余票。 |
| “我想去新疆” | 出发地已知时，先明确建议具体城市，例如“先以乌鲁木齐作为到达城市，可修改”，点亮可修改预览；缺条件时再追问，说明历史数据版本。 |
| “我想要途经郑州” | 继承当前目标与未修改条件，加入郑州约束，重算铁路路线、日期及历史车次/票价匹配，更新回复、地图和保存方案。 |

“上海到新疆”的例子以当前行程或已知默认出发地为上海为前提；没有依据时不能替所有用户暗定上海。新疆是区域，乌鲁木齐是 AI 明确给出的建议，具体车站还需匹配并可修改。

“途经郑州”必须体现在实际线路中，但仅经过、换乘与下车停留应分开表达。用户若把郑州作为访问/停留节点，则沿用默认一日且可调整的规则；语义不清时针对性补问，不自动把所有铁路经停节点变成停留一天。

### 7.3 缺失信息与相关回复

| 情况 | 应答与处理 |
| --- | --- |
| 缺出发地 | 继承当前行程中已明确的信息；没有可用上下文时问从哪里出发，不凭空补值。 |
| 缺目的地 | 询问想去哪里，可给相关表达示例，保留已说出的偏好。 |
| 仅有区域目标 | 先建议明确目的城市、说明建议并给可修改预览，不直接把区域当作车站。 |
| 缺日期或必要行程条件 | 几何条件足够时可先给实际铁路路线预览，再询问；历史价格可按版本展示，不把预览或历史数据说成当前售票查询结果。 |
| 偏好或途经含义不清 | 回显可理解部分，补问会改变路线或日期的关键条件，不清空当前方案。 |
| 没有固定关键词或意图尚不明确 | 按语义给出相关引导，不因未命中固定词表直接失败，不丢失已有行程。 |
| 历史数据载入失败、无线路几何或无匹配车次 | 说明具体限制与可调整项，保留有效输入和此前方案，不假称新路线已生成。 |

### 7.4 多轮修改与共同上下文

对话、地图与列表共用一份当前行程。用户明确说“途经郑州”“改去喀什”等即授权该次修改，应保留未改动的偏好、起终目标和其他条件，重算并说明变化；不要求每句明确修改都再次确认。

AI 自行提出的城市与条件必须标为建议，不能覆盖用户已明确的约束。用户删除或替换过的条件不能被旧记忆重新加回。旧异步请求后返回时不得覆盖更新后的方案，不能出现新回复配旧地图、旧历史车次匹配冒充新结果。

### 7.5 保存与恢复

个性化输出及后续调整必须能够保存，重新打开后可以恢复并继续补充。至少保存意图和偏好、起终目标/建议目的城市、城市顺序、停留、匹配车站、方案与解释，以及铁路几何来源、历史时刻/票价的数据版本与来源时间；回放行程还保存日期锚点 D0/R0、参考服务日及原始时刻，避免恢复时随当天日期重新映射。

区分用户明确条件、AI 建议与历史数据事实。保存成功或失败有反馈，恢复时说明版本和来源时间；版本或行程改变时重算历史数据匹配，不触发实时票价/余票查询。访问和引用须校验属主，不把其他用户行程或偏好带入上下文。

跨新行程是否自动沿用长期偏好、默认出发地从哪里取得、访客和跨设备保存方式及保留期限尚待确认；不把一次输入永久推断为用户画像。

## 8. 主页实际铁路路线与地图联动

主页地图同时承担城市组线和 AI 方案展示。AI 给出方案、插入途经城市或用户改线后，地图应点亮相应的实际铁路走向，联动具体站点与分段结果，不只增加一个目的地点或更新一段回复文字。

真实线路需要有来源的连续铁路几何和区间对应关系。选定具体车次后，几何须有可核对的车次运行路径匹配依据。不能在不支持目标客运的线路上仅求几何最短路就声称存在可乘坐方案。

城市直线、道路/公交算路、把经停站坐标直接串成折线、AI 生成坐标都不能替代本项目要求的实际铁路路线。铁路底图上能看到轨道，也不等于已经按当前行程正确点亮线路。

几何缺失、不连续或无法与目标区间对应时，显示具体缺失段并说明该能力尚未完成；可以保留已知站点和此前有效方案，但不能用示意线补成通过验收的“实际铁路路线”。

线路几何、历史时刻衔接和历史票价分别说明；本轮不判断可售性。几何条件足够时可点亮实际铁路预览，车次/时刻/价格按明确版本展示。几何主来源已确定为同一 GTFS 包中的关联 shapes，覆盖与准确性逐样例核验；此前仅内存抽查，未完成地图叠加或运行验收。预算调整不降低实际铁路几何要求。

### 8.1 本地点位与高德地点查询

地点基础库维护本地城市与铁路站。地图底图使用高德 JS API，普通地点查询使用独立的高德 Web 服务。历史车次、时刻、票价、铁路几何和用户行程沿用各自的数据来源。

| 对象 | 数据职责 |
| --- | --- |
| 城市 | 本地提供名称/别名、行政归属与位置，作为城市组线输入；不宣称尚未导入的城市已被覆盖。 |
| 火车站/高铁站 | 本地提供所属城市、站名/别名、坐标、铁路标识及已知服务类型；“高铁站”不构成独立重复实体，不凭名称推断列车服务。 |
| 其他地点 | 通过高德 API 按需搜索、定位与查看详情，不预置或批量抓取全国其他地点；不自动写入本地城市/车站基础表。 |
| 历史铁路与线路几何 | 按各自来源组织历史方案和实际铁路高亮；高德地点返回不能代替铁路时刻、票价或轨迹。 |

1. 输入时匹配本地城市和铁路站。用户点击「搜索高德地点」后才发起普通地点查询。结果区分本地城市、铁路站和高德地点，展示城市和地址以便区分同名地点。
2. 高德其他地点可用于地图定位与地点信息；如需加入铁路行程，先关联并核对本地城市/铁路车站，沿用已有明确意图或用户选择，不把任意兴趣点当作上下车站，也不因此新增景点/住宿行程规划。
3. 本地基础数据与外部返回保留来源和坐标系，绘图时转换到统一坐标系，避免直接混用造成站点或轨迹偏移。不能用城市中心点补成未知车站坐标。
4. 前端通过项目后端访问本地基础数据及高德 Web 服务查询；后端保管 Web 服务密钥、校验查询条件并控制请求频率。按明确搜索动作触发，不逐字无节制请求；不新增缓存基础设施或自动开通收费服务。
5. 高德超时、无结果、权限或配额不足分别给简短反馈；保留本地城市/站点检索、已有行程和已取得的有效数据。无结果不能描述为没有铁路或没有车次；地点接口失败也不等同于铁路规划失败。
6. 普通地点查询只返回本次查询的结果，保留高德地点 ID 供当前界面使用。长期保存引用见 [OPEN-15](feature-list.md)。上线前按部署账号核对调用权限、出口 IP 与可用配额。

#### 普通地点查询接口

`GET /api/places?q=地点名` 接收去除首尾空白后 1～64 个字符的关键词，全国范围查询高德 Web 服务 v3 关键字接口。每次请求取第一页，最多 10 个可用地点。后端在同一实例按 1 秒间隔发出请求，等待上游响应最多 5 秒。Web 服务 Key 通过 `AMAP_WEB_SERVICE_KEY` 注入后端。高德响应使用 GCJ-02。 [高德关键字搜索](https://lbs.amap.com/api/webservice/guide/api/search/) · [高德错误码](https://lbs.amap.com/api/webservice/guide/tools/info)

200 返回 `source: "AMAP"`、`coordinateSystem: "GCJ-02"` 和 `items`。每项包含 `poiId`、`name`、`longitude`、`latitude` 以及可空的 `city`、`district`、`address`。站点归属和铁路站码仍来自本地目录。无匹配项时返回空 `items`，响应使用 `Cache-Control: no-store`。查询结果保存在本次页面状态。

错误沿用统一错误体 `{"error":{"code","message"}}`。

| HTTP | 错误码 | 条件 |
| --- | --- | --- |
| 422 | `VALIDATION_FAILED` | 关键词空白或超长。 |
| 503 | `PLACE_SEARCH_NOT_CONFIGURED` | 后端缺少 Web 服务 Key。 |
| 503 | `PLACE_SEARCH_PERMISSION_DENIED` | 高德拒绝访问、Key 权限或平台不符。 |
| 429 | `PLACE_SEARCH_QUOTA_EXCEEDED` | 高德账户、Key 或请求频率受限。 |
| 429 | `PLACE_SEARCH_RATE_LIMITED` | 触发本服务请求间隔。 |
| 504 | `PLACE_SEARCH_TIMEOUT` | 高德请求或响应超时。 |
| 502 | `PLACE_SEARCH_UNAVAILABLE` | 上游服务异常或响应无法使用。 |

### 8.2 GTFS shapes 的关联、裁剪与坐标

1. 从已选运行实例的 `trip_id` 找到同版本 `shape_id`，按 `shape_pt_sequence` 连接轨迹点；不把 `trip_short_name` 直接当 shape ID，不跨版本拼接。缺 shape 的车次可保留文字时刻，地图缺失段明确留空。
2. shape 通常对应整趟车；只乘中间区间时，结合 `stop_times.stop_sequence` 与站点位置定位实际上/下车边界，裁剪后再绘制。该包的 `stop_times.txt` 与 `shapes.txt` 未提供 `shape_dist_traveled`，不能直接按站序下标切 shape 点数组；有回折、重复经过或无法唯一定位时，需按顺序核对，失败则标记该段几何未核实。
3. GTFS 站点与 shape 使用 WGS84；绘制到高德底图时统一转换到目标坐标系，避免漏转/重复转换。保留原始数据与坐标来源，转换不改写参考服务日或车站身份。
4. 选中样例检查站点贴合、轨迹方向/连续性、是否沿铁路以及上下车区间一致；不能仅凭轨迹点数或 GTFS 文件名宣称准确。点位插值或稀疏几何导致的偏差如实记录，不用站点直线补齐。
5. 后端读取预生成包并按所选样例提供必要区间几何，前端复用既定路线组件；不把整个全国 `shapes.txt` 发到浏览器，也不增加 Python/前端打包器等运行要求。合成 UI 夹具仍只用于视觉和状态测试。

## 9. 最简模拟预订与技术边界

模拟流程仅为：选择方案 → 展示交通摘要与模拟标识 → 用户确认 → 生成模拟预订记录。明确标注模拟，不收款、不产生真实票额占用或真实车票；重复确认避免重复记录。

旅行计划与模拟记录独立，生成或修改行程不自动预订。当前不建设旧版库存维护、并发抢最后一张票、十分钟锁座、倒计时、模拟支付网关、复杂取消/超时/退票状态机、手续费及票务管理后台。真实购票、支付和出票未纳入当前实施范围。

保留 Java 17、Spring Boot 3、MyBatis、MySQL 8、原生 ES Modules、Session 鉴权及不增加前端构建步骤的现有约束。高德 Web 服务及 LLM 等服务端密钥通过环境变量配置，不写入前端或版本库。其他地点查询已指定高德 API，铁路时刻/关联 shapes 按 §6.1 固定来源；独立票价来源、底图 SDK 和存储细节仍待细化，不在本需求同步中安装或更换技术栈。

旧设计、前端及后端初始化已归档；当前尚无新版可运行实现，预留说明或配置不代表业务已实现。历史业务规则和接口不自动延续为新版默认验收。

## 10. 后续验收方向

以下是详细设计和独立 review 的依据，不代表已经实现或运行通过。

1. **地图组线**：依次点选城市得到同顺序行程；系统自动匹配真实车站，允许用户调整，不静默删改城市或限制为固定换乘次数。
2. **历史数据事实**：每段车次、实际发到站、时刻和匹配席别的历史区间价可追溯到来源与版本；缺失价格标未知，已知合计不冒充完整总价；不依赖外部真实票务 API。
3. **自然日停留**：周一到达、默认周二可续程；前段跨日或修改停留后，后续日期与历史车次匹配同步更新，不按满 24 小时误算，数据版本与日期映射清楚。
4. **换乘最少**：在相同用户约束、历史时刻可衔接的条件下，比较全程换乘次数。有可续程的分段直达时仍比较可能减少全程换乘的方案。同站换车计次，同一运行实例途经或分段不增加次数，不以余票筛选。
5. **AI 个性化**：哈尔滨慢节奏、新疆建议目的城市等表达能产生相应方案与相关解释，不能只换一段描述或丢失偏好。
6. **多轮与缺失信息**：补充“途经郑州”后继承仍有效条件、更新同一行程；缺必要信息或关键词时能继续任务，不要求用户重述全部内容。
7. **实际铁路点亮**：地图几何对应真实铁路走向和目标乘坐区间；不以直线、道路、站点折线或假坐标通过验收；数据不足时明确未完成段。
8. **保存恢复**：方案、个性化输出和后续调整可恢复，属主隔离有效；历史数据版本与来源时间保留，条件/版本改变可重算，回复/地图/保存版本一致。
9. **异常与模拟**：无匹配车次、不可衔接、价格缺失、跨日、数据载入失败等有明确结果；模拟记录不依赖旧库存交易模块，也不触发真实交易。
10. **余票后置**：本轮无实时或模拟余票查询、筛选与状态展示，不默认全部有票；界面与 AI 说明历史参考属性，不输出可售承诺。
11. **地点分工**：本地城市/站点能按名称、别名及城市归属查找，同站普速/高铁不重复；其他地点按需查询高德并消歧、定位，不混入铁路车站身份。高德失败时本地查询与已有行程保留；混合来源坐标对齐，地点结果不冒充铁路轨迹。开发阶段需验证请求路由、密钥边界、异常和坐标一致性。

12. **GTFS 与回放初测**：固定包版本可追溯；逐车参考日历有效，服务日与途中上车日不混淆，超过 24 小时时刻和自然日停留正确；非零/零日期偏移、跨月年/闰日及越界有明确结果，恢复保留锚点；缺 shape、区间裁剪与坐标转换按真实样例核验。用 §6.3 的少量场景逐步验证，不宣称全国通过。

开发验收仍需落实样例基准日期、同次数次级排序与衔接参数；数据源与日期映射规则已定。要实际验证本地导入、字段匹配、规划/回放和铁路几何，不以收费票务接口或实时余票实测作为本轮通过条件。

## 11. 仍需确定的事项

- 独立历史区间/席别票价来源、适用版本与字段完整性；GTFS 不含票价，缺失按未知，不选定或开通收费票务 API。
- 固定 GTFS 的城市归属来源与版本见[目录数据和来源](city-replay.md#目录数据和来源)。目标站点坐标精度及车站服务标签继续按真实样例核验。
- 目标样例的 shape 覆盖、沿铁路准确性、区间裁剪和坐标转换实测；主来源及 `trip_id → shape_id` 关联已定。
- 高德地点 API 的具体版本、账号权限/配额及引用保存策略；其他地点使用高德已确认，底图 SDK 未定。
- 按有效历史服务日复验日期回放、跨日衔接及统一偏移；首个可出发自然日的查询窗口见 §4.2。
- 同城跨站的接驳数据来源和最小衔接缓冲、零天停留与 AI“途经”的停留语义。
- 同等换乘次数时的次级排序、席别/人数等必要输入；当前不设计候补、售罄等余票处理。
- 默认出发地来源、访客/跨设备保存、保留期限与长期偏好使用方式。
- 前后端详细设计、接口契约、UI 与实际接入验证；本文件不代替这些产物。

不再将以下已确认内容列为待定：铁路限定、不设固定换乘上限、自然日停留、区域目标建议预览、换乘次数主排序、历史票价及余票后置、本地城市/铁路站点和高德地点分工，以及指定 GTFS/关联 shapes、固定多日版本少量路线初测与统一日偏移回放。
