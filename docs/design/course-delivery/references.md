## 4. Oracle．MySQL 8.0 Reference Manual：InnoDB Transaction Model

来源：[Oracle．MySQL 8.0 Reference Manual：InnoDB Transaction Model](https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-model.html)。访问日期：2026-11-17。

该章节说明了InnoDB事务模型中多版本与行级锁的作用，为共享数据库中的一致性设计提供依据。本项目据此将快照保存限制在短事务内，并要求更新同时检查用户、计划和期望版本；普通读取不会自动防止另一窗口覆盖，所以版本条件必须显式存在。请求唯一身份和结果核对用于处理写入成功但响应丢失的情况，不能仅靠界面禁用按钮。此处把数据库能力用于行程与模拟快照，没有恢复旧库存扣减范围。来源只支持机制选择，具体表结构、隔离行为、冲突错误和故障恢复仍需在所选版本上通过并发及超时试验验证。

## 5. MobilityData．General Transit Feed Specification：Schedule Reference

来源：[MobilityData．General Transit Feed Specification：Schedule Reference](https://gtfs.org/documentation/schedule/reference/)。访问日期：2026-11-17。

规范定义车站、车次、停站时刻、开行日历与轨迹之间的关联，并明确服务日可以包含超过二十四小时的时刻。这直接影响本项目区分列车参考服务日、途中上车日与用户行程日期的模型，避免把累计时刻截断成普通钟点。轨迹通过车次关联，再根据乘坐区间裁剪；可选距离字段的存在与单位需要逐包核对，不能将停站序号当作轨迹数组下标。本项目采用统一自然日偏移保存回放锚点，这是基于规范语义形成的应用设计，并非规范提供的旅行规划算法。具体铁路包的完整性、坐标准确性和实际走向仍须另行核验。

## 6. wensimehrp．chinese-railway-gtfs：项目说明与数据约定

来源：[wensimehrp．chinese-railway-gtfs：项目说明与数据约定](https://github.com/wensimehrp/chinese-railway-gtfs)。访问日期：2026-11-17。

上游说明列出数据涵盖铁路线路、站点坐标和列车时刻，明确不包含票价，并说明坐标采用WGS八四及数据许可来源。这使本项目把固定GTFS作为时刻和关联轨迹输入，同时将历史区间价与城市归属留给独立来源，避免从没有价格的数据包生成报价。初测固定版本而非随上游每日更新，记录下载来源、内容哈希、适用日期和必要署名，才能复查旧行程。仓库说明并不保证目标车次每天开行或每段轨迹准确，本设计因此保留逐车日历、区间裁剪与坐标检查。该来源支持选源理由，不替代本地导入和地图样例实证。

## 8. OpenAI．Structured Model Outputs

来源：[OpenAI．Structured Model Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)。访问日期：2026-11-17。

官方指南介绍按预定结构返回模型结果，并讨论拒绝和不完整输出的处理。这影响了本项目将自然语言修改表达为带版本的受限提议：完整结果先做结构、实体和允许字段校验，再交确定性规划服务验证，最后更新共享行程。结构匹配只能限制形状，不能保证车站、票价或时刻真实，因此工具事实、用户条件与模型建议必须分别保存。兼容OpenAI形式的第三方接口也不自动具有相同约束能力，应逐供应方试验拒绝、截断与非法返回。该资料支持受控编排的边界，没有据此引入额外智能体框架或授权模型自行保存、预订和执行交易。
